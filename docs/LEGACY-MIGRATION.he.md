# מעבר בטוח מהניקוד הישן ל־Supabase הקיים

## מה מוכן ומה עדיין צריך לבדוק

הקבצים שסופקו כוללים 100 רשומות ב־`scores_rows.csv` ו־15 ב־`daily_scores_rows.csv`. כל 115 הרשומות עברו הכנה מקומית ללא דחיות או מזהים כפולים. זה **לא מוכיח** שהייצוא כולל את כל הטבלאות או את כל הרשומות. לא בוצעה שום פעולה במסד הנתונים.

הטבלאות החדשות למשחק הן `sn_runs`,‏ `sn_entries`,‏ `sn_rate_limits`. נוסף ארכיון נפרד `sn_legacy_entries`. ה־RPC‏ `sn_board` קורא רק את `sn_entries`, ולכן רשומות ישנות לא נכנסות לדירוג המאומת של v20. הצגת טבלת עבר נפרדת תהיה שינוי נוסף; עצם הייבוא לא מציג את הניקוד הישן במשחק.

קובצי CSV אינם מוכיחים סוגי SQL, מפתחות או הרשאות. שמות המקור `public.scores` ו־`public.daily_scores` במיפוי מבוססים על שמות קובצי הייצוא; יש לאמת אותם ואת מזהה הפרויקט לפני הרצה. אין כאן SQL כללי שמשנה את מבנה הטבלאות הישנות.

## 1. גיבוי ובדיקת מבנה

1. ודאו שאתם בפרויקט הקיים הנכון. אל תשלחו מפתחות API, סיסמת מסד או `service_role` בצ׳אט/בקובץ ציבורי.
2. שמרו גיבוי מלא/נקודת שחזור לפי אפשרויות הפרויקט ובדקו שאפשר לשחזר לסביבה נפרדת. ייצוא CSV של שתי טבלאות הוא עותק נתונים שימושי, אך אינו גיבוי מלא של מסד, הרשאות וסכימה.
3. הריצו ב־SQL Editor את `supabase/inspect-existing-schema.sql`. זו עסקת קריאה בלבד: טבלאות, עמודות, PK/FK, דגלי RLS ושמות מדיניות. היא אינה קוראת שורות, סודות או ביטויי מדיניות. שמרו את התוצאות פרטית. הרשאות תצוגת metadata עשויות להשפיע על מה שנראה.
4. ודאו שאין התנגשות בשם `sn_*`. אם יש, עוצרים ובודקים; לא מוחקים או מחליפים אובייקט קיים. סקרו את ה־RLS וההרשאות של הטבלאות הישנות בנפרד: המיגרציה אינה מתקנת אותן ואינה משנה אותן.
5. ייצאו את כל הרשומות מכל אחת משתי טבלאות המקור, כולל כל העמודות והמזהה המקורי. השוו ספירת שורות במסד מול הייצוא כדי לזהות מגבלת 100/1000 שורות או סינון. אם יש PK מספרי גדול, עדיף לייצא אותו כמחרוזת JSON; כלי ההכנה שומר גם מספרי PK מדויקים מתוך ה־JSON המקורי.

## 2. המיפוי המדויק של הייצוא שסופק

- `id` ← זהות מקור קבועה, בצירוף פרויקט + סכימה + טבלה. אותו ID בטבלה אחרת אינו אותה רשומה.
- `player_name` ← `name`, ללא קיצור או החלפת שם.
- `score` ← הניקוד ההיסטורי המקורי. אין חישוב מחדש לפי v20.
- `time_ms` ← `time` בשניות בחלוקה מפורשת ב־1000. גם זמן אפס נשמר כפי שהוא; אין תיקון מנחש.
- `created_at` ← `submitted_at`, המרת כתיב PostgreSQL ל־RFC3339 תוך שמירת האזור והשבר המקוריים. הטקסט המקורי נשמר גם הוא.
- `health`,‏ `status`,‏ `version` ← `null`, כי המידע אינו קיים בייצוא. `deaths` אינו חיים שנותרו, אינו מספר פגיעות בגרסה החדשה, ואינו מוכיח ניצחון או הפסד.
- `level_id`,‏ `challenge_date`,‏ `deaths` וכל עמודה נוספת נשמרים ב־`raw_json`; רשומות יומיות נשארות מזוהות לפי טבלת המקור והתאריך המקורי. לא מאחדים לוחות שונים.
- כל הרשומות מסומנות `legacy_unverified` ו־`verified_board_eligible=false`. אין נתוני replay או הוכחה לאימות הישן. שינוי התאימות/הדירוג בעתיד דורש החלטה מפורשת ותכנון נפרד.

המיפויים מוכנים ב־`tools/legacy-scores-mapping.json` וב־`tools/legacy-daily-scores-mapping.json`. עברו עליהם מול הסכימה בפועל. המזהים בהם אינם סיסמאות; הנתונים עצמם חייבים להישאר פרטיים.

## 3. הכנה מקומית וסקירת הייבוא

נדרש Node.js מודרני (18 ומעלה). אין התקנת חבילות, אין חיבור לרשת ואין גישה למסד. בחרו תיקיית פלט פרטית **מחוץ למאגר/חבילת הפריסה**, שלא קיימת עדיין:

```sh
node tools/legacy-prepare-csv.mjs /private/scores_rows.csv tools/legacy-scores-mapping.json /private/review-scores --review-sql
node tools/legacy-prepare-csv.mjs /private/daily_scores_rows.csv tools/legacy-daily-scores-mapping.json /private/review-daily --review-sql
node --test tools/legacy-prepare-tests.mjs
```

לייצוא JSON כללי, אחרי יצירת מיפוי מפורש מהדוגמה:

```sh
node tools/legacy-prepare.mjs /private/export.json /private/mapping.json /private/review-json
```

כל תיקייה מכילה עותק מקור, מיפוי, `normalized.json` ו־`report.json`. ב־CSV בלבד, `--review-sql` מוסיף `review-import.sql` לקריאה ואישור, **לא להרצה אוטומטית**. הכלים מסרבים לדרוס תיקיית פלט קיימת. קוד יציאה 2 פירושו שורות נדחו; קוד 1 הוא שגיאה שחוסמת הכנה/כתיבה. עם `--review-sql`, דחיות או שינויים ביחס לפלט הקודם חוסמים SQL; הריצו בלי הדגל כדי להפיק דוח מפורט.

בדוח בדקו:

- `input = accepted + rejected`, אפס דחיות ואפס קבוצות כפולות.
- ספירות המקור המלאות מול הייצוא. בקבצים שסופקו: 100 + 15, לא טענה לספירה החיה.
- כמה דוגמאות פרטיות של מיפוי שם, ניקוד, זמן, תאריך ועמודות נוספות; אפסים וחריגים נשארים מקוריים.
- `raw_json` שומר בדיוק את שורת JSON המקורית. ב־CSV הוא שומר את כל ערכי השורה כמחרוזות; עותק ה־CSV המקורי נשמר במלואו ובדיוק. SHA-256 מקשר לקובץ ולשורות.
- מפתח `legacy_<sha256>` נגזר רק מזהות המקור, לא מהשם או מהניקוד. כל עותקי אותו PK נדחים במקום לבחור אחד בשקט. שינוי פרויקט/טבלה/טיפוס PK במיפוי משנה את הזהות, ולכן לא משנים אותם בין הרצות בלי סקירה.

אל תעלו CSV, פלט JSON או SQL המכיל שורות למאגר, ל־`dist`, ל־Netlify, לאתר ציבורי או לחבילת המסירה. פלט SQL כולל מידע אישי בדיוק כמו הגיבוי.

## 4. פריסה מוסיפה בלבד וייבוא מבוקר

1. נסו תחילה בסביבת בדיקה/עותק מבודד של הפרויקט, עם גיבוי ובדיקת שחזור.
2. לאחר סקירת התנגשויות, החילו פעם אחת את `202611050001_leaderboard.sql` ואז `202611050002_legacy_archive.sql`. אין `DROP`, אין שינוי לטבלת המקור ואין הענקת קריאה ציבורית לארכיון. אין להריץ שוב מיגרציה שכבר נרשמה; אל תפתרו התנגשות באמצעות מחיקה.
3. השלימו את הגדרות השרת והסודות לפי מדריך הפריסה הראשי, ואז בדקו משחק חדש, שמירת תוצאה, retry ודירוג. מפתחות שירות בצד השרת בלבד.
4. פתחו את שני קובצי `review-import.sql`, בדקו את היעד והספירות, ורק אחרי אישור הריצו ב־SQL Editor כבעל הרשאות מסד מתאים. הקוד כותב רק ל־`public.sn_legacy_entries`.
5. כל קובץ הוא עסקה אחת: זהות קיימת עם נתונים זהים מדולגת; נתונים שונים באותה זהות גורמים לשגיאה ולביטול כל העסקה. נעילת הארכיון מונעת מרוץ בין בדיקה לכתיבה. אין overwrite, אין מחיקה ואין עדכון לרשומה ישנה. שתי הטבלאות מיובאות בשתי עסקאות נפרדות, ולכן יש לוודא הצלחה של כל אחת.
6. בדקו ספירות לפי מקור, כל דגלי האימות, סכום הניקוד ומספר שדות null מול הפלט הפרטי. בדקו שוב שהלוח החדש לא השתנה בגלל ארכיון העבר.

דוגמת בדיקה אחרי הייבוא, לקריאה בלבד:

```sql
select source->>'table' as source_table,
       count(*) as rows,
       sum((normalized->>'score')::numeric) as score_sum,
       count(*) filter (where normalized->>'health' is null) as unknown_health,
       count(*) filter (where normalized->>'status' is null) as unknown_status,
       bool_and(verification='legacy_unverified' and not verified_board_eligible) as excluded_from_verified
from public.sn_legacy_entries
group by source->>'table';
```

## 5. השלמת פערים לאחר הפריסה

אם המשחק הישן ממשיך לכתוב, שמרו נקודת חתך/חלון מעבר מוגדר. ייצאו שוב את **כל** שורות המקור והשוו לפלט הקודם; אין להסתמך על תאריך בלבד, כי ייתכנו עריכות או זמנים זהים:

```sh
node tools/legacy-prepare-csv.mjs /private/scores-fresh.csv tools/legacy-scores-mapping.json /private/review-scores-catchup /private/review-scores/normalized.json
```

`new_keys` הן מועמדות חדשות, `unchanged_keys` מאפשרות rerun בטוח, `changed_keys` דורשות החלטה פרטנית, ו־`missing_previous_keys` הן סימן לבדיקה בלבד, **לא הוראות מחיקה**. השוו גם בין מקורות וודאו שהייצוא השני מלא. לאחר סקירה, ניתן להריץ שוב לאותה תמונה בתיקייה חדשה עם `--review-sql`; הרשומות שכבר קיימות וזהות מדולגות. אין לפתור שינוי רשומה באמצעות שינוי ID או מחיקת הארכיון.

במעבר הסופי, השביתו כתיבה ישנה רק כחלק מפעולת פריסה מאושרת ומוגדרת, ייצאו פעם אחרונה, השלימו את הפערים והשוו ספירות. אין צורך להפסיק קליטת ריצות v20 כדי לסקור את הארכיון, אך יש לבדוק השפעת נעילת הארכיון על ייבוא מקביל.

## 6. חזרה לאחור

אם פריסת המשחק החדש נכשלת, החזירו את גרסת האתר/הגדרותיה הקודמות לפי נוהל הפריסה. השאירו את הטבלאות החדשות ואת התוצאות שכבר נכתבו, כדי שלא לאבד מידע. אם ייבוא SQL נכשל לפני commit, כל אותו קובץ מתבטל; בדקו את השגיאה לפני ניסיון נוסף. הייבוא השני עשוי להיכשל אחרי שהראשון הצליח, והרצה חוזרת של הראשון בטוחה כשהנתונים לא השתנו.

אל תמחקו טבלאות ישנות, אל תשחזרו גיבוי על גבי כתיבות חדשות ואל תבצעו מחיקת ארכיון אוטומטית. אם לאחר commit נדרש תיקון, שמרו גיבוי ודוח המפתחות של האצווה והכינו שינוי נקודתי נפרד לאישור. אין בקבצים האלה תסריט מחיקה הרסני.

## גבולות הבדיקה

כלי ההכנה ומקרי הקצה נבדקים מקומית. הכנת 115 הרשומות הצליחה. הסכימה החיה, שלמות הייצוא, ההרשאות בפועל, ייבוא ל־PostgreSQL ופריסה ל־Netlify דורשים בדיקה בסביבה האמיתית; אין להסיק שהם כבר בוצעו מהצלחת ההכנה.
